# Codex 插件式漫画审校工作台设计

## 1. 目标

为 `repair-comic-continuity` Skill 增加一个简单、可视化、可恢复的人工审校入口，让用户和朋友能在 Windows Codex 中完成以下工作：

- 在输入漫画上圈画画面问题并用自然语言批注；
- 选择人工审查模式或全自动模式；
- 用同一个按钮把当前阶段提交给 Codex；
- 查看真实处理进度；
- 对处理后的全部输出页进行强制人工复核；
- 在输出图上继续圈画并提交二次修改；
- 将人工发现的漏检、误改和修复结果纳入现有证据化学习闭环，提高后续全自动检测能力。

工作台只简化操作，不削弱现有 Skill 的哈希、证据、独立复核、精确文件映射和最终只读验证门禁。

## 2. 非目标

- 不制作可脱离 Codex 独立修图的软件；
- 不让工作台直接持有或调用模型密钥；
- 不创建第二套与 `human_visual_auto_text` 重叠的人工模式；
- 不让生图模型直接排中文；
- 不用缩略图、OCR 相等或自然语言声明代替全分辨率证据；
- 不允许用户批注未经验证就自动变成全局规则；
- 不在本设计阶段修改图片、开发插件或运行正式生产流程。

## 3. 产品形态

采用一个可安装和分享的 Codex 插件，插件包含三个边界清晰的组件：

1. **审校 App**：显示图片、圈画、批注、输入/输出对比和简化进度。
2. **本地桥接工具**：创建项目会话、原子保存标注、提交阶段事件、读取真实门禁状态和恢复中断会话。
3. **现有 Skill**：继续负责小说和参考图取证、画面审核、任务调度、无字重绘、文字引擎、独立复核、学习和最终发布门禁。

所有使用者必须安装并登录 Codex。工作台没有 Codex 时只能查看和保存已有标注，不能执行修复。

## 4. 极简界面

普通界面只保留用户真正需要的操作：

- 选择项目；
- 选择模式；
- `正确/通过并下一页`；
- 圈画和批注；
- `提交给 Codex`；
- 查看输入/输出对比和处理进度。

推荐布局：

```text
┌──────────┬──────────────────────┬──────────────┐
│ 页面缩略图 │      高清图片画布       │   当前页批注   │
│ 状态与筛选 │  缩放、拖动、圈画、撤销  │  自然语言说明  │
├──────────┴──────────────────────┴──────────────┤
│ 正确/通过并下一页          提交给 Codex          │
└───────────────────────────────────────────────┘
```

高级证据、哈希、JSON、规则范围和审查记录默认折叠。只有发生阻塞时才显示简明原因和可处理动作。

## 5. 项目启动与模式

新建运行时只选择一次模式，首次提交后锁定模式。需要切换模式时创建新运行，但允许复用哈希有效的项目索引。

### 5.1 人工审查模式

复用现有 `human_visual_auto_text`：

- 用户必须把每张输入页标记为正确或有问题；
- 有问题的页面可以有多个圈画区域和多条批注；
- 用户只写“哪里不对、怎么改”，Codex 在不改变用户语义的前提下补全结构化字段；
- 只有用户选择的页面可以进入画面整页重绘；
- 未选择页面不能被 Codex 自行扩大为画面重绘范围；
- 所有输入页仍进入内嵌文字引擎流程。

工作台自动生成和校验：

- `evidence/human_visual_selection.json`；
- `evidence/human_issue_annotations.json`。

### 5.2 全自动模式

- Codex 按现有场景簇、人物矩阵、小说、参考图和相邻页证据自动发现画面问题；
- 内嵌文字引擎独立处理所有页面文字；
- 自动处理结束后不得直接正式输出，必须进入全量人工输出复核；
- 人工发现的漏检和误改成为证据化学习输入。

## 6. 单一提交按钮

界面只有一个 `提交给 Codex` 按钮。按钮根据项目状态自动判断动作：

- 输入审查阶段：提交首次处理；
- 输出复核阶段：提交未通过页面的二次修改；
- 没有新增或变更批注：拒绝重复提交；
- 正在处理中：按钮禁用；
- 有未审页面、缺少批注说明或哈希漂移：显示具体页数并阻止提交。

用户不需要选择“首次处理”或“第几次二修”。修复轮次由后台状态管理。

## 7. 圈画与批注

### 7.1 用户操作

- 支持矩形、自由圈画和多边形；
- 支持一页多个问题；
- 支持整页问题；
- 支持撤销、删除、修改批注和自动保存；
- 不把圈线烧录进原图或输出图。

### 7.2 后台记录

每条批注至少绑定：

- 批注 ID；
- 输入相对路径与源图 SHA-256；
- 一个或多个标准化区域；
- 用户原始说明；
- Codex 补全但可追溯的目标、问题大类、具体特征、观察状态和要求状态；
- 项目、场景簇、运行编号、修复轮次和时间。

自由圈画和多边形同时保留原始路径，并生成兼容现有 V5.5 的 `bbox_norm`。不得只保存屏幕像素坐标。

## 8. 项目索引与增量处理

首次打开新项目时建立一次内容寻址索引：

- 输入图片和自然排序；
- 小说哈希与可定位片段；
- 人物参考图哈希；
- 场景簇、人物状态和稳定画风锚点；
- 文字区域和样式锁所需源证据。

后续人工详细批注运行优先复用哈希有效的索引，只重新核对问题页、相邻页、涉及人物、相关小说片段和受影响场景簇。任何输入图、小说、参考图或关键规则发生变化时，相关缓存必须失效；不能用旧缓存静默通过。

增量处理是同一 `human_visual_auto_text` 模式的优化路径，不增加第二个用户可见模式。

## 9. 画面与文字的严格顺序

### 9.1 画面问题页

```text
提取并锁定原普通文字及样式
→ 生成整页无普通文字候选
→ 独立检查人物、道具、场景、构图和画风
→ 无字画面通过
→ 内嵌文字引擎统一加字
→ 文字和背景 QA
→ 人工输出复核
```

- 生图模型不得直接生成中文；
- 无字画面未通过前不得排字；
- 二修涉及画面时必须重新走无字候选，不得在已有文字成品上直接重绘；
- 经审核需要保留的拟声艺术字和画面文字与普通对白分开管理。

### 9.2 仅文字问题页

画面保持不变，只运行 `page_reset_preserve_style`。文字引擎必须保存字体、颜色、大小、位置、方向、行数、行框、间距、描边、旋转、锚点和对话框几何。

### 9.3 文字清除路由

```text
安全纯色背景 → 确定性填充
普通纹理背景 → LaMa
LaMa 不安全或处理失败 → GPT Image 2 局部编辑
GPT Image 2 仍失败 → evidence_blocked
```

GPT Image 2 的模型 ID 使用 `gpt-image-2`，只允许删除指定普通文字并补全原背景。它不得生成中文、增加对话框、改动圈定区域外内容或借机重绘整页。

每个 GPT Image 2 清除候选必须检查残字、接缝、线条连续性、人物和分镜保护、修改像素范围与背景一致性。失败候选不得进入排字或成为参考图。同一失败族两次失败后暂停继续调用。

## 10. 处理状态

工作台只显示来自控制器和证据文件的真实状态，不显示估算出来的假百分比：

```text
画面审核/修复：8/12
文字引擎处理：46/98
待人工复核：5
被阻塞：1
预计剩余生图调用：3
```

可展开查看的阻塞原因包括：缺少参考、小说定位不确定、文字样式置信度不足、文字溢出、LaMa 和 GPT Image 2 均失败、规则冲突或连续两次同类失败。

## 11. 强制人工输出复核

两种模式都必须执行：

- 第一轮处理后，全部输出页必须标记为通过或圈画问题；
- 未完成复核的页面不能进入最终发布；
- 输入和输出支持并排、滑块和透明叠加对比；
- 二修后只重新复核本轮被修改的页面；
- 已通过页面锁定，后续不能重新生成或重新排字。

输出批注自动区分：

- 全自动漏检；
- 已发现但未修好；
- 修复新增问题；
- 改坏原来正确的内容；
- 文字、文字背景或排版问题。

输出二修批注必须绑定原批注 ID、源图哈希、当前候选哈希和修复轮次，不能覆盖上一轮历史。

## 12. 经验学习

直接复用现有 `human_issue_learning.py`、`failure_learning.json` 和 V5.5 闭环控制器：

1. 人工输入或输出批注先成为观察到的失败证据；
2. 修复后绑定不同的候选哈希和独立结果复核；
3. 只有同时通过失败页正向回归、正确页保护、相似变体和独立复核后，规则才可生效；
4. 规则按 `page → cluster → project → skill_candidate` 逐级提升；
5. 同范围冲突规则阻塞，不能静默选择最新规则；
6. 被拒绝候选永远不能成为参考图。

工作台不要求用户管理规则，只显示：

```text
本次记录问题经验：12
已验证并生效：5
仍在观察：7
```

项目规则可用于同项目后续全自动运行。跨电脑永久生效的 Skill 规则仍需回归测试、独立复核、签名发布和插件更新，不能自动上传用户图片或私有项目数据。

## 13. 精确输出与保护

最终发布必须保证：

- 输入和输出数量都等于 `N`；
- 相对路径、文件名、Unicode 拼写、大小写、扩展名和子目录完全一致；
- 正确页字节级复制或按页面类别受控处理；
- 已通过页在二修中保持锁定；
- 不漏页、不增页、不重新编号、不拍平目录；
- 候选目录与最终输出目录隔离；
- 最终验证只读，不得在验证阶段补证据、修图或改状态。

## 14. 自动保存、中断和接管

- 每次圈画、批注修改和页状态变化立即自动保存；
- 关闭 App 或 Codex 后可从最后状态恢复；
- 原 Codex 任务存在时恢复原任务；
- 原任务不可用时允许新任务接管项目，但必须重新核对项目、运行和全部当前文件哈希；
- 原图和输出图始终保持干净，标注作为独立覆盖层保存；
- 批注批次、学习写入和提交事件都使用原子事务，禁止半批写入。

## 15. 错误处理和额度保护

- 同一 `(场景簇, 任务类型, 失败族)` 连续两次失败后暂停该通道；
- 暂停后先由 Codex 记录失败原因、修正策略和重新开放证据；
- 只让确认有画面问题的页面调用整页生成；
- GPT Image 2 只作为 LaMa 不安全或失败后的文字清除备用通道；
- 无新批注、无状态变化或正在运行时拒绝重复提交；
- 阻塞页不得用弱修补、白色矩形、字体回退或自然语言声明强行通过。

## 16. 安装、分享与版本

- 插件包同时携带 Skill、审校 App、本地桥接工具、资源和校验器；
- 朋友只安装一个插件，不分别安装标注器和 Skill；
- 每个项目记录插件、Skill、规则库和文字引擎版本；
- 打开旧项目时先做兼容性检查；
- 更新插件不得静默改变已完成运行的证据；
- 发布包需要插件结构验证、Skill 验证、完整测试、签名证书和可复现版本标识。

## 17. 测试与验收

### 17.1 界面和状态

- 人工模式不能遗漏未审输入页；
- 两种模式都不能绕过全量首次输出复核；
- 同一按钮在输入提交、二修提交、运行中和无变化时行为正确；
- 一页多圈、整页圈画、撤销、删除和恢复不丢失；
- 模式提交后不可静默切换；
- 关闭和重新打开后状态一致。

### 17.2 数据和门禁

- 选择清单和批注清单路径、顺序、区域和哈希完全正确；
- 批注缺字段、越界、重复、乱序或哈希漂移时失败关闭；
- 学习批次和二修批次原子写入；
- 缓存只在依赖哈希完全有效时复用；
- 规则冲突、两次同类失败和证据不足均能阻塞。

### 17.3 画面和文字

- 画面重绘候选无普通文字，且未通过时不会进入排字；
- 仅文字页不改变画面；
- LaMa 失败时只对目标文字区域调用 GPT Image 2；
- GPT Image 2 区域外改动、残字、接缝或线条破坏必须被拒绝；
- 排字保持所有 `style_lock` 字段，文字溢出不得强行保存；
- 拟声艺术字和画面文字不会被普通文字流程误删。

### 17.4 最终输出

- 输入输出精确一一对应；
- 已通过页面在后续轮次不改变；
- 所有人工复核、页面 QA、场景簇 QA、学习记录和最终报告顺序正确；
- 最终只读验证能够发现缺页、改名、旧哈希、伪造通过和未解决批注。

## 18. 交付边界

第一版只实现上述必要闭环，不增加多人在线协作、云端项目管理、复杂规则编辑器、训练新模型或公开托管服务。界面保持极简，复杂性留在插件、Skill 和证据层。

设计通过后，下一阶段应先编写实施计划，再按测试优先顺序开发和验证；不得直接从本设计跳到正式生产处理图片。
